# План: своя VPN-панель (Xray + Hysteria2 + AmneziaWG)

Рабочее название проекта: **panel** (переименуем позже).

## 1. Цели и рамки

**Что это:** open-source панель для личного использования. Через один интерфейс управляет серверами Xray, Hysteria2 и AmneziaWG. В перспективе к ней добавится своё Android-приложение.

**Цели**
- Понятный современный интерфейс: дашборд, пользователи, ноды, инбаунды, логи, настройки.
- Один пользователь (устройство или человек) получает доступ сразу к нескольким протоколам по одной ссылке.
- Нормальные логи: структурированные, вживую, с фильтрами, аудит изменений.
- Hysteria2 работает наравне с Xray, а не прикручен сбоку.
- Amnezia уже установлена на сервере штатно (Docker) и остаётся под управлением официального приложения. Панель её не трогает: вкладка «Amnezia» только показывает статус, логи и клиентов.
- В карточке и на странице пользователя видны все варианты подключения: Xray, Hysteria2 и ключ Amnezia (выданный приложением Amnezia).
- Конфиги без ручной правки импортируются в v2rayNG, Hiddify, sing-box, Clash/Mihomo; ключ Amnezia — в Amnezia VPN.
- Установка одной командой, обновление одной командой.

**Не цели (сознательно не делаем)**
- Биллинг, оплаты, реселлеры, тарифы, продажа доступа.
- Тысячи пользователей и сложное шардирование. Ориентир: 1–10 серверов и до ~100 пользователей.
- Логирование посещённых сайтов по умолчанию. Эта функция опциональная и по умолчанию выключена.

> «Подписка» дальше означает только техническую ссылку `/sub/<token>`. По ней клиент сам обновляет конфиги, к оплате она отношения не имеет.

### Целевой сервер
Ubuntu 22.04, 1 vCPU, 2 ГБ RAM, 25 ГБ SSD. Что из этого следует:
- Панель, агент, Xray и Hysteria2 работают на этом же сервере (режим `--with-local-agent`), рядом с уже установленными контейнерами Amnezia.
- Бюджет памяти наших компонентов: панель + агент ~60 МБ, Xray ~40–80 МБ, Hysteria2 ~30 МБ, итого ~200 МБ. Плюс то, что уже занимают Docker и Amnezia (замерить на сервере).
- Основной способ установки: systemd без Docker, чтобы не тратить ресурсы. Docker Compose остаётся опцией.
- Фронтенд и бинари собираются в CI или локально, на VPS ставится готовый релиз.
- Ротация логов и лимит размера SQLite обязательны (по умолчанию не больше 1 ГБ на логи).
- Swap-файл 1–2 ГБ создаётся установщиком, если его нет.

### Тестовая среда (локально, на Windows 11 Pro)
- **Hyper-V VM** с Ubuntu 22.04 и теми же ресурсами, что у VPS (1 vCPU, 2 ГБ, 25 ГБ), чтобы сразу видеть реальное потребление.
- Сеть через **External switch** (мост в локальную сеть). Тогда к VM можно подключиться с телефона по Wi-Fi и проверить v2rayNG, Hiddify, Amnezia и AmneziaWG вживую.
- Перед экспериментами делаем чекпоинт VM, откат занимает секунды.
- **Копия реальной ситуации:** на VM ставим Amnezia тем же способом, что на сервере (официальное приложение → «свой сервер» по SSH), с теми же протоколами. Тогда сосуществование с Docker проверяем на VM, а не на рабочем сервере.
- Цикл разработки:
  1. На Windows кросс-компилируем `GOOS=linux go build`.
  2. Копируем бинарь на VM через `scp` (или скриптом `make deploy-vm`).
  3. На VM перезапускаем сервис через systemd.
- Фронтенд разрабатываем через `vite dev` на Windows с прокси API на VM.
- Reality в локальной сети работает. Для проверки ACME и Hysteria2 с настоящим сертификатом в конце понадобится домен и VPS (или самоподписанный сертификат и `insecure` на клиенте).

## 2. Решение по скелету

Ничего не форкаем, пишем своё. Идеи берём из готовых проектов:

| Откуда | Что берём как идею |
|---|---|
| Marzban / PasarGuard | модель «пользователь + лимиты + ссылка подписки», хосты в подписке |
| Remnawave | разделение панели и ноды, современный UI |
| 3x-ui | мастер настройки Reality, простая установка |
| Hiddify | выдача подписки в разных форматах по User-Agent |

Почему не форк: ни один проект не умеет нормально работать с несколькими ядрами под одним пользователем, а Hysteria2 и AWG пришлось бы встраивать с переделкой ядра проекта.

**Лицензия:** по умолчанию MIT (можно сменить на AGPL-3.0, если хочется, чтобы форки оставались открытыми). Ядра запускаются отдельными процессами, поэтому их лицензии наш код не ограничивают:
- Xray: MPL-2.0;
- Hysteria: MIT;
- amneziawg-go: MIT.

## 3. Архитектура

```
┌──────────────── Panel (control plane) ────────────────┐
│  Web UI (React, встроен в бинарь)                     │
│  REST API + WebSocket   ←→   SQLite                   │
│  /sub/<token> — подписки, страница пользователя с QR  │
└───────────────┬───────────────────────────────────────┘
                │ gRPC + mTLS (панель → агент)
┌───────────────┴──────────────┐
│ Agent (data plane, Go)       │  — на каждом сервере
│  reconcile: желаемое → факт  │
│  ┌──────┐ ┌─────────┐ ┌─────┐│
│  │ Xray │ │Hysteria2│ │ Amn ││  — адаптеры (Amnezia —
│  └──────┘ └─────────┘ └─────┘│    только чтение из Docker)
│  сбор трафика, онлайн, логов │
└──────────────────────────────┘
```

**Ключевые принципы**
1. **Декларативная синхронизация.** Панель отправляет агенту *полное желаемое состояние* ноды: инбаунды, пользователи и версия. Агент сам вычисляет разницу и применяет её. Повторная отправка ничего не ломает, а после обрыва связи состояние догоняется автоматически.
2. **Нода работает без панели.** Агент кэширует последнее состояние на диске. Если панель недоступна, VPN продолжает работать. Авторизация Hysteria2 проверяется локально в агенте.
3. **Режим одного сервера.** В режиме `panel --with-local-agent` агент запускается внутри процесса панели. Отдельная установка не нужна, а код тот же самый.
4. **Единый интерфейс адаптера:**
   ```go
   type Adapter interface {
       Protocol() string
       Apply(ctx, inbound Inbound, users []UserAccess) error // идемпотентно
       Traffic(ctx) ([]TrafficDelta, error)                 // дельты с прошлого вызова
       Online(ctx) ([]OnlineEntry, error)
       Health(ctx) HealthStatus
       Logs() <-chan LogLine
   }
   ```

## 4. Протоколы и адаптеры

### 4.1 Xray
- Протоколы: **VLESS + XHTTP (основной)** в двух вариантах: с Reality (без домена, на 443) и через CDN (домен + TLS). Плюс все остальные транспорты Xray (полный список — в 4.5): какие реально работают, определяем тестами.
- XHTTP в мастере:
  - режимы `auto` / `packet-up` / `stream-up` / `stream-one` с подсказкой, какой когда нужен (за CDN обычно `packet-up`, напрямую с Reality — `auto`);
  - случайный `path`, padding (`xPaddingBytes`), настройки мультиплексирования (`xmux`) с безопасными дефолтами;
  - «разделённый» режим (`downloadSettings`): загрузка через CDN, скачивание напрямую через Reality — позже, в экспертном режиме.
  - Совместимость клиентов: XHTTP понимают Xray-клиенты (v2rayNG, v2rayN, Hiddify, Streisand и т. п.), а sing-box — нет. Для sing-box подписки XHTTP пропускаем и показываем это в UI; в своём Android-приложении берём libXray.
- Управление: xray-core работает отдельным процессом под присмотром агента. Пользователи добавляются и удаляются через gRPC API (`HandlerService` с `AlterInbound`), без перезапуска. При изменении инбаундов конфиг генерируется заново и Xray перезапускается.
- Трафик: `StatsService.QueryStats` с шаблоном `user>>>{email}>>>traffic>>>*` и сбросом счётчиков. Онлайн: статистика online-пользователей в свежих версиях Xray (проверить в фазе 0).
- Мастер Reality (для XHTTP и TCP): генерация x25519-ключей и shortId, подсказки SNI, проверка, что целевой домен поддерживает TLS 1.3 и H2.

### 4.2 Hysteria2
- Ядро: официальный сервер `apernet/hysteria` отдельным процессом.
- Авторизация: `auth.type: http`. Hysteria обращается к локальному HTTP-эндпоинту агента (`127.0.0.1`), агент проверяет пароль пользователя по своему кэшу и возвращает `{ok, id}`.
- Трафик и онлайн: встроенный API `trafficStats` с секретом (`/traffic?clear=1`, `/online`, `/kick`).
- Настройки в UI: порт, сертификат (ACME или свой), obfs salamander, masquerade, bandwidth, port hopping (диапазон портов через iptables/nftables).

### 4.3 Amnezia: существующая установка, не трогаем
На сервере уже стоят Docker-контейнеры Amnezia, установленные штатно через официальное приложение. **Ими управляет только приложение Amnezia.** Наша панель живёт рядом и ничего в них не меняет:
- не перезапускает, не обновляет и не удаляет контейнеры;
- не правит их конфиги и файлы;
- не трогает Docker, его сети и его правила iptables.

**Вкладка «Amnezia» в нашей панели только читает данные:**
- Контейнеры `amnezia-*`: статус, аптайм, образ, порты, CPU/RAM. Данные берутся через Docker API только на чтение (`/containers/json`, `/stats`).
- Логи контейнеров (`docker logs`) попадают во вкладку «Логи» как источник `amnezia`.
- Клиенты AWG: имя, последний handshake, трафик. Данные читаются командой `awg show` внутри контейнера и из файла `clientsTable`, в котором приложение хранит имена. Это только чтение; насколько это удобно и безопасно, проверяем в фазе 0. Если неудобно, во вкладке остаются статус и логи.
- Уведомление в Telegram, если контейнер Amnezia упал.
- Подсказка: «Клиентами управляет приложение Amnezia → Поделиться доступом».

**Все варианты подключения в одном месте:**
- В карточке пользователя есть поле «Ключ Amnezia». Ключ `vpn://...` создаётся в приложении Amnezia («Поделиться»), и его вставляют в это поле.
- На странице пользователя `/sub/<token>` этот ключ показывается рядом с Xray и Hysteria2: текстом, QR-кодом и кнопкой «скопировать».
- Панель хранит ключ зашифрованным (`user_access`, `protocol = amnezia_key`) и только показывает его. Включить или выключить такой доступ панель не может: это делается в приложении Amnezia. Лимиты по сроку и трафику на него не действуют, в UI так и подписано.
- В общую ссылку подписки Amnezia не попадает: v2rayNG, Hiddify и Clash такой формат не понимают.

**Позже, по желанию (выключено по умолчанию):** управлять AWG-клиентами в том же формате, что и приложение (`wg0.conf` + `clientsTable` внутри контейнера), чтобы приложение видело созданных нами клиентов, а лимиты работали. Только после бэкапа и явного включения в настройках.

### 4.3.1 Сосуществование с Docker и Amnezia (обязательные правила для агента)
- **Порты.** Перед созданием инбаунда агент проверяет занятые порты (`ss -tulpn`, включая `docker-proxy`) и не даёт занять порт Amnezia. Если 443 уже занят контейнером Amnezia (например, их XRay), мастер Reality предлагает другой порт.
- **Firewall.**
  - Цепочки Docker (`DOCKER*`, `FORWARD`, NAT) не трогаем и не очищаем.
  - Свои правила ставим только в отдельной таблице nftables `inet panel`.
  - Если на сервере есть Docker, ufw автоматически не включаем: вместе они известны конфликтами.
- **sysctl.** Свои значения пишем в отдельный файл `/etc/sysctl.d/90-panel.conf`. `ip_forward` и всё, что нужно Docker, никогда не выключаем.
- **WARP и policy routing** не затрагивают подсети Docker и Amnezia. Пустить Amnezia через WARP можно только отдельной опцией, выключенной по умолчанию.
- **Docker.** Наша панель ставится через systemd и Docker не требует. Установщик не обновляет и не перезапускает Docker.
- **Ресурсы.** Перед установкой агент показывает, сколько RAM уже занимают контейнеры Amnezia, и предупреждает, если на наши компоненты остаётся мало.
- **Перед установкой на реальный сервер:** снапшот VPS у хостера и проверка, что после перезагрузки Amnezia продолжает работать.

### 4.4 Набор протоколов и стратегия устойчивости

Неуязвимого протокола нет. Блокируют не «заголовки», а совокупность признаков: репутацию IP хостера, необычные порты и UDP, статистику пакетов (размеры, тайминги, «TLS внутри TLS»), несовпадение SNI и IP, активные проверки сервера. Поэтому ставка не на один протокол, а на **несколько непохожих транспортов** и **автоматическое переключение** в клиенте.

| Протокол | Как выглядит снаружи | Сильные стороны | Слабые места | Когда |
|---|---|---|---|---|
| VLESS + XHTTP + Reality | обычный HTTPS/HTTP2 к реальному сайту, трафик похож на обычные HTTP-запросы | по опыту — стабильно работает сейчас; нет своего домена и сертификата; нет длинного «непрерывного» TLS-потока | IP дата-центра; блокировка IP целиком; не поддерживается sing-box | **фаза 1, основной** |
| VLESS + XHTTP через CDN | обычный HTTPS к сайту за Cloudflare или другим CDN | IP сервера скрыт за CDN: блокировка IP сервера не помогает | нужен домен; чуть медленнее; зависит от CDN | фаза 2, запасной при блокировке IP |
| VLESS + TCP + Reality + Vision | обычный TLS 1.3 к реальному сайту | самый быстрый; Vision убирает признак «шифрование внутри шифрования» | длинные TLS-сессии к «чужому» IP могут вызывать подозрения — проверим тестами | фаза 1, рядом с XHTTP |
| Hysteria2 | QUIC/HTTP3 (или случайный UDP с obfs salamander) | скорость на плохих каналах, port hopping | UDP режут или душат; «случайный UDP» с salamander сам по себе подозрителен | фаза 2, для скорости |
| AmneziaWG | WireGuard с мусорными пакетами и изменёнными заголовками | быстрый, сигнатуры WireGuard не видны | UDP; управляется приложением Amnezia | уже есть |
| Shadowsocks-2022 | полностью случайный поток | очень простой и лёгкий | эвристики «полностью зашифрованного трафика» | опция, без приоритета |
| NaiveProxy / AnyTLS (sing-box) | HTTP/2 или TLS с отпечатком настоящего Chrome, с padding | очень похож на обычный браузер | нет в Xray: нужно ещё одно ядро (sing-box), домен и сертификат | фаза 2, через ядро sing-box |
| Каскад через сервер в РФ | трафик к российскому IP | спасает при «белых списках» (мобильный интернет пускает только к разрешённым IP) | второй сервер, двойная задержка | фаза 3 (мульти-нода, выход `node:`) |

**Как это работает вместе:**
- Подписка отдаёт клиенту **все** способы, а sing-box/Clash/Hiddify получают группу `urltest` / `fallback`: клиент сам выбирает работающий и быстрый, при блокировке переключается без участия пользователя. В своём Android-приложении то же самое.
- В карточке пользователя видно, через какой протокол он реально подключался, на странице `/sub/<token>` — подсказка «если не работает, попробуй этот».
- Мастер инбаунда предупреждает о типичных ошибках: Reality на нестандартном порту, SNI сайта без TLS 1.3/H2, SNI, который хостится в той же сети (лучше брать сайт, похожий на «соседа» по IP).
- Слабые варианты (VMess без TLS, WebSocket без CDN и т. п.) в мастере доступны, но с пометкой «легко обнаружить», чтобы их можно было включить для сравнения в тестах.

### 4.5 Полный список протоколов и порядок реализации

Решение: делаем **все** практичные варианты, а какие лучше работают, определяем тестами. Чтобы это не превратилось в хаос, у каждого протокола в мастере есть понятная карточка: «как выглядит снаружи», «что нужно» (домен, CDN, UDP), «каким клиентом подключаться».

**Ядро Xray** (основное, фаза 1–2):

| Протокол | Транспорт | Защита | Что нужно | Фаза |
|---|---|---|---|---|
| VLESS | XHTTP | Reality | ничего | 1 |
| VLESS | TCP (RAW) + Vision | Reality | ничего | 1 |
| VLESS | gRPC | Reality | ничего | 1 |
| VLESS | XHTTP | TLS | домен, можно за CDN | 2 |
| VLESS | WebSocket / HTTPUpgrade | TLS | домен, обычно за CDN | 2 |
| VLESS | XHTTP «разделённый» (вверх через CDN, вниз через Reality) | Reality + TLS | домен + CDN | 2 (эксперт) |
| Trojan | TCP / XHTTP / WebSocket / gRPC | TLS или Reality | для TLS — домен | 2 |
| VMess | WebSocket / gRPC / XHTTP | TLS | домен; устаревший, для совместимости | 2 |
| Shadowsocks-2022 | TCP + UDP | собственное шифрование | ничего | 2 |

**Отдельные ядра:**

| Протокол | Ядро | Что нужно | Фаза |
|---|---|---|---|
| Hysteria2 (+ obfs salamander, port hopping) | официальный hysteria | UDP; сертификат (LE или самоподписанный + pin) | 2 |
| TUIC v5 | sing-box | UDP; сертификат | 2 |
| AnyTLS | sing-box | сертификат | 2 |
| NaiveProxy | sing-box | домен + сертификат | 2 |
| ShadowTLS v3 (обёртка над Shadowsocks) | sing-box | ничего (маскируется под чужой сайт) | 2 |
| AmneziaWG | уже стоит, приложение Amnezia | — | только показ ключей |

sing-box добавляем как **третье ядро** с тем же интерфейсом `Adapter`, что у Xray и Hysteria. Это ещё ~30–50 МБ RAM на сервере; ядро запускается только если включён хотя бы один его протокол.

**Удобство тестирования:**
- Кнопка «Тестовый набор»: одним действием создаёт на сервере по одному инбаунду каждого протокола, которому не нужен домен, на свободных портах, и тестового пользователя со всеми доступами. Удаляется тоже одной кнопкой.
- На странице `/sub/<token>` у каждого способа есть QR и пометка, каким клиентом его открыть.
- В журнале и статистике видно, по какому протоколу шёл трафик, — сравнивать удобно.

### 4.6 Домены

Домен нужен не всем протоколам: Reality и сертификат Let's Encrypt на IP обходятся без него. Он нужен для протоколов «с TLS» (Trojan/VLESS/VMess + TLS, NaiveProxy, AnyTLS, TUIC, Hysteria2 с настоящим сертификатом) и обязателен для CDN. В настройках три варианта:

| Вариант | Как | Что даёт | Ограничения |
|---|---|---|---|
| Без домена | — | Reality, сертификат LE на IP | нет CDN; TLS-протоколы на IP-сертификате |
| Бесплатный DDNS (DuckDNS и аналоги) | вводишь поддомен и токен; панель сама обновляет IP и выпускает сертификат через DNS-01 (TXT-запись по API DuckDNS) | настоящий сертификат на имя, все TLS-протоколы | **через Cloudflare CDN не работает**: в Cloudflare можно добавить только свой домен, не поддомен чужой зоны. Бесплатные DDNS-зоны часто попадают в списки подозрительных, вся зона может блокироваться целиком |
| Свой домен | покупаешь (дешёвые зоны — от ~$1–3 за первый год), делегируешь в Cloudflare, вводишь API-токен | всё, включая CDN: XHTTP/WebSocket через Cloudflare, скрытие IP сервера | платно; регистратор знает владельца |

- Сертификаты на домен панель выпускает и продлевает сама (ACME DNS-01 через API DuckDNS/Cloudflare, без открытого 80-го порта).
- Для панели и подписки домен можно не использовать вообще, чтобы не связывать имя с сервером.
- Поддержка DuckDNS — фаза 2 (вместе с TLS-протоколами), Cloudflare — фаза 2 (вместе с CDN).

## 5. Пользователи, лимиты, подписки

- **Пользователь:** имя, заметка, статус (active / disabled / expired / limited), срок действия (опционально), лимит трафика (опционально) с периодом сброса (никогда, день, неделя, месяц), токен подписки.
- **Доступы:** у пользователя N доступов, по одному на инбаунд. Учётные данные (UUID, пароль, ключи AWG, IP) генерируются автоматически.
- **Применение лимитов:** раз в минуту панель агрегирует трафик. Если пользователь превысил лимит или истёк срок, он отключается, и это событие попадает в журнал.
- **Подписка `/sub/<token>`:**
  - формат определяется по User-Agent или по `?format=`: base64 со ссылками (v2rayN/v2rayNG/Hiddify), Clash/Mihomo YAML, sing-box JSON;
  - в браузере открывается страница пользователя: остаток трафика, срок, QR-коды для каждого протокола, `.conf` и `vpn://` для Amnezia, инструкции по клиентам;
  - **хосты:** у одного инбаунда может быть несколько адресов для подписки (домен, CDN, IP), каждый со своим именем.
- **Контроль устройств:** вместо жёсткого лимита показываем онлайн-сессии и IP-адреса. Для личного использования этого достаточно.

## 6. Настройки: маршрутизация, WARP, DNS и всё остальное

### 6.1 Как это сделано в 3x-ui и что меняем

В 3x-ui есть вкладка «Настройки Xray»:
- галочки «заблокировать торренты, рекламу, частные IP», «IPv4 для Google», «WARP для доменов»;
- таблицы Outbounds, Routing, Balancers и DNS;
- кнопка регистрации WARP;
- «Расширенный шаблон», то есть сырой JSON всего конфига Xray.

Проблемы такого подхода:
1. Всё работает **только для Xray**. Hysteria2 и Amnezia остаются без маршрутизации.
2. Шаблон JSON общий и легко ломается: одна ошибка, и Xray не стартует. Нет ни проверки перед применением, ни отката.
3. Нет истории изменений: непонятно, что поменялось и когда.
4. Галочки, таблицы и сырой JSON смешаны, и не видно, какая настройка «победит».

Что делаем у себя:
- **Одна модель правил для всех ядер.** Правила описываются один раз, а «компилятор» переводит их в формат каждого ядра. UI честно показывает, где правило работает, а где нет.
- **Применение с проверкой и откатом.** Перед применением панель показывает итоговый конфиг и diff, конфиг проверяется (`xray run -test`), затем применяется. Если ядро не поднялось за 15 секунд, агент сам откатывает прошлую версию.
- **Версии конфигурации.** Каждое применение сохраняется, откат на любую версию в один клик.
- **Два режима.** «Простой» с пресетами и понятными формами по умолчанию. «Эксперт» с редактором JSON (Monaco + JSON Schema, подсветка ошибок) для отдельных блоков. JSON вставляется как переопределение поверх сгенерированного, а не вместо него.
- **Уровни настроек:** глобально → профиль ноды (шаблон) → конкретная нода → инбаунд. В каждом поле видно, откуда взято значение («унаследовано из профиля»), и его можно переопределить.

### 6.2 Выходы (outbounds)

Это «куда отправлять трафик». Они общие для всех правил:

| Выход | Что это |
|---|---|
| `direct` | напрямую с IP сервера |
| `block` | заблокировать |
| `warp` | через Cloudflare WARP (см. 6.4) |
| `ipv4` / `ipv6` | напрямую, но только через IPv4 или IPv6 (например, Google по IPv4, чтобы не было капчи) |
| `proxy:<имя>` | внешний SOCKS5, HTTP, VLESS или Shadowsocks: другой VPS, резидентный прокси и т. п. |
| `node:<имя>` | каскад через другую нашу ноду (позже, в мульти-ноде) |
| `balancer:<имя>` | группа выходов с выбором по задержке или доступности (Xray observatory) |

Для каждого выхода есть кнопка «проверить»: агент делает запрос через этот выход и показывает внешний IP, страну и задержку.

### 6.3 Правила маршрутизации

**Модель правила:**
```
Rule {
  name, enabled, order
  match: { domains[], geosite[], ips[], geoip[], ports, network(tcp|udp),
           protocol(bittorrent|...), users[], inbounds[] }
  action: outbound tag
}
```
- Таблица правил с перетаскиванием для порядка (срабатывает первое подходящее), переключателем вкл/выкл и поиском по категориям geosite с автодополнением.
- **Пресеты** включаются одной галочкой и раскрываются в обычные правила, которые потом можно поправить:
  - блокировать частные IP (`geoip:private`) — включено по умолчанию, чтобы через VPN нельзя было сканировать сеть хостера;
  - блокировать BitTorrent — защита от жалоб хостеру;
  - блокировать рекламу и трекеры (`geosite:category-ads-all`);
  - отправить через WARP сервисы, которые блокируют IP дата-центров или регион: ChatGPT/OpenAI, Gemini, Netflix и т. п.;
  - Google через IPv4;
  - блокировать исходящий SMTP (порт 25) — защита от спама с твоего IP.
- **Правила для отдельных пользователей:** например, «пользователь X весь через WARP». Это работает только в Xray (по email пользователя), в UI так и подписано.

**Во что компилируется:**

| Ядро | Как применяются правила | Что поддерживается |
|---|---|---|
| Xray | `routing.rules` + `outbounds` | всё |
| Hysteria2 | встроенный ACL (`warp(geosite:openai)`, `reject(geoip:private)`) + outbounds `direct` / `socks5` / `http` | домены, geosite/geoip, IP, порты; без правил по пользователям и протоколам; поддержку geosite/geoip в ACL проверить в фазе 0 |
| Amnezia | **не применяются**: маршрутизацией Amnezia управляет её приложение | — |

У каждого правила видны значки «Xray ✓ · Hy2 ✓».

**Продвинутый режим (позже, по желанию):** трафик Hysteria2 заворачивается в Xray (SOCKS), и тогда **все** правила, включая правила по пользователям, работают и для Hy2. Цена — дополнительный проход через Xray и нагрузка на 1 ядро CPU, поэтому только как опция. Пустить сюда же Amnezia (policy routing подсети её контейнера) можно только отдельной опцией, выключенной по умолчанию, потому что это меняет сеть рядом с контейнерами Amnezia.

### 6.4 WARP

- **Регистрация в один клик.** Агент регистрирует бесплатный WARP-аккаунт через API Cloudflare (как wgcf). Есть поле для ключа WARP+. Ключи хранятся зашифрованными.
- **Один WARP на оба ядра.** Агент поднимает системный интерфейс `warp0` (WireGuard есть в ядре Ubuntu 22.04) с отдельной таблицей маршрутизации. По умолчанию трафик через него не идёт, поэтому SSH, Docker и контейнеры Amnezia не затрагиваются. Его используют:
  - Xray: выход `freedom` с `sockopt.interface: warp0`;
  - Hysteria2: выход `direct` с `bindDevice: warp0`;
  - Amnezia: не используется (только отдельной опцией, см. 6.3).
- **Режимы:**
  1. выключен;
  2. только по правилам (рекомендуется);
  3. весь трафик через WARP;
  4. только IPv6 через WARP (если у VPS нет IPv6).
- **Статус:** подключён или нет, внешний IP WARP, страна, задержка, кнопки «перевыпустить ключи» и «проверить».
- Если WARP упал, трафик по WARP-правилам идёт напрямую (fallback; настраивается: напрямую или блокировать) и отправляется уведомление.

### 6.5 DNS

- **DNS сервера** (как сам сервер резолвит домены пользователей):
  - список апстримов: DoH (`https://1.1.1.1/dns-query`), DoT, обычный UDP, локальный;
  - стратегия: IPv4 и IPv6, только IPv4, предпочитать IPv4;
  - DNS по доменам: например, `geosite:openai` резолвить через DNS WARP;
  - статичные `hosts`;
  - кэш, таймауты.
- **Компиляция:** Xray → блок `dns`; Hysteria2 → `resolver` (UDP/TCP/TLS/HTTPS).
- **DNS для клиентов:**
  - sing-box/Clash: блок DNS в шаблоне подписки (см. 6.7);
  - Amnezia: DNS задаётся в её приложении, панель его не меняет.

### 6.6 Гео-базы (geoip.dat / geosite.dat)

- Источник на выбор:
  - Loyalsoldier — общий;
  - runetfreedom/russia-v2ray-rules-dat — с категориями под РФ (`geosite:ru-blocked`, `geoip:ru-blocked`);
  - свой URL.
- Автообновление по расписанию (по умолчанию раз в сутки), проверка целостности, хранение прошлой версии для отката.
- Ядра используют общие файлы: и Xray, и ACL Hysteria2.
- Поиск по категориям в UI: «какие категории содержат домен example.com».

### 6.7 Клиентская маршрутизация (в подписке)

Серверные правила решают, куда сервер отправит трафик. Клиентские правила решают, что клиент вообще пустит в VPN, а что откроет напрямую. Это важно для использования из РФ: российские сайты и банки открываются напрямую, остальное идёт через VPN.

- Шаблоны для sing-box и Clash/Mihomo с пресетами:
  - «RU напрямую» (`geosite:category-ru`, `geoip:ru`);
  - «Только заблокированное через VPN» (`ru-blocked`);
  - «Всё через VPN»;
  - «Локальная сеть напрямую».
- Выбор шаблона глобально и для отдельного пользователя.
- Заголовки подписки: `profile-title`, `profile-update-interval`, `subscription-userinfo` (клиенты показывают трафик и срок).
- Для base64-подписок (v2rayNG) правила передать нельзя, там будет подсказка, как настроить маршрутизацию в самом клиенте.
- Для Amnezia: split-tunneling настраивается в самом приложении Amnezia, у нас будет только инструкция.

### 6.8 Ядра

- Версия каждого нашего ядра (Xray, Hysteria2), кнопка «обновить до последней» или выбор версии из списка релизов, откат. Для Amnezia показываем версии образов без кнопок: обновляет её приложение.
- Уровень логов, access-лог (по умолчанию выключен).
- Политики Xray: таймауты (handshake, connIdle), буферы, сбор статистики.
- Sniffing (определение домена по TLS, HTTP, QUIC) — включено по умолчанию, без него не работают доменные правила.
- Статус процесса, аптайм, потребление RAM и CPU, кнопка перезапуска.

### 6.9 Система ноды

Агент делает это сам, с отчётом «применено / уже было»:
Все пункты учитывают правила сосуществования с Docker и Amnezia из 4.3.1.
- **Сеть:** BBR + fq, тюнинг sysctl (буферы UDP для Hysteria2/QUIC) в отдельном файле `/etc/sysctl.d/90-panel.conf`. IPv6 вкл/выкл — только с предупреждением, если он используется контейнерами.
- **Firewall (только своя таблица nftables `inet panel`):**
  - порты инбаундов открываются и закрываются автоматически вместе с инбаундами;
  - порты Amnezia и правила Docker не трогаем;
  - порт панели можно ограничить списком IP;
  - port hopping Hysteria2 через nftables.
- swap, синхронизация времени (NTP), часовой пояс.
- Опционально: fail2ban для SSH, смена порта SSH (с предупреждением и проверкой, что новый порт доступен, прежде чем закрыть старый).
- Сводка «здоровье системы»: свободное место, RAM, загрузка, сертификаты (сколько дней до истечения), сеть.

| Безопасность | админы, пароли, 2FA, сессии (список активных, «выйти везде»), белый список IP |

### 6.11 Как это ложится в архитектуру

- В панели хранятся только **намерения**: правила, выходы, DNS, пресеты.
- Пакет `internal/panel/compile` превращает их в итоговые конфиги каждого ядра для конкретной ноды. Это чистые функции без побочных эффектов, поэтому они хорошо покрываются тестами («правило X → такой-то кусок JSON Xray и такая-то строка ACL»).
- Агент получает готовые конфиги в `NodeState`, проверяет их, применяет и откатывает при ошибке.
- Экран «Итоговый конфиг» показывает в режиме только для чтения, что реально уйдёт в каждое ядро. Это удобно для отладки.

### 6.12 Обновление ядер и панели

**Откуда и как:**
- Раз в сутки панель проверяет релизы на GitHub: XTLS/Xray-core, apernet/hysteria, позже sing-box. Pre-release и черновики пропускаются.
- Новая версия скачивается во временную папку, сверяется контрольная сумма из релиза (как в `install-xray.sh` / `install-hysteria.sh`), запускается `version`.
- Для Xray текущий конфиг проверяется новой версией (`xray run -test`). Если новая версия его не принимает, обновление отменяется с понятной причиной, например «в новой версии поле X переименовано».
- Переключение атомарное: бинари лежат по версиям, `cores/xray/26.10.31/`, `cores/xray/26.11.02/`, а ссылка `current` указывает на рабочую. Ядро перезапускается. Если оно не поднялось или не прошло проверку здоровья за 15 секунд, ссылка возвращается на прошлую версию.
- Хранятся две последние версии. Откат на предыдущую — одна кнопка.
- Гео-базы (geoip/geosite) обновляются тем же механизмом (см. 6.6).

**Режимы для каждого ядра:**
1. «Только уведомлять» (по умолчанию): значок «доступна 26.11.02» на обзоре и уведомление в Telegram.
2. «Автоматически»: обновлять ночью в заданное окно, например 04:00–05:00, с откатом при проблеме и уведомлением.
3. «Закрепить версию»: не обновлять, пока не снимешь закрепление.

**Права:** панель работает не от root, а `/usr/local` для неё только для чтения. Поэтому установленные ею ядра живут в её папке данных (`/var/lib/panel/cores/...`). Скрипты `install-*.sh` остаются для первой установки и ручного восстановления.

**Обновление самой панели** работает так же: релиз из нашего репозитория на GitHub, проверка контрольной суммы, замена бинаря, перезапуск через systemd, откат при неудаче. Это заработает, когда появятся релизы на GitHub.

### 6.13 Экспорт настроек и переезд на другой VPS

**Резервная копия — один зашифрованный файл** `panel-backup-2026-11-04.pbk`. Внутри:
- база данных: пользователи, подключения, ключи Reality, сертификаты и пароли obfs Hysteria, правила, журнал аудита. Снимок берётся через `VACUUM INTO`, так что он целостный даже на работающей панели;
- `panel.json`: порт, секретный путь панели, путь подписок, адрес для клиентов;
- TLS-сертификат и ключ панели;
- версии ядер (сами бинари не копируются, на новом сервере они скачиваются заново).

Шифрование: пароль → scrypt → AES-256-GCM. Без пароля файл бесполезен, поэтому его можно спокойно хранить в Telegram или облаке.

**Как сделать:**
- из интерфейса: «Настройки → Обслуживание → Скачать резервную копию», с повторным вводом пароля администратора;
- командой на сервере: `panel backup create -out backup.pbk`;
- по расписанию: локально (храним N последних) и/или в Telegram (см. 6.10).

**Переезд на новый VPS:**
1. На новом сервере ставим панель скриптом установки.
2. Восстанавливаем копию: `panel backup restore backup.pbk`, либо загружаем файл на экране первого запуска вместо создания администратора.
3. Панель спрашивает новый адрес для клиентов (IP или домен), ставит нужные ядра нужных версий, применяет конфиги и печатает адрес панели. Порт и секретный путь сохраняются, если порт на новом сервере свободен.

**Что увидят клиенты.** Ключи, UUID и пароли не меняются, меняется только адрес сервера.
- **Если клиенты подключены по домену** (DuckDNS или свой домен, см. 4.6), достаточно перенаправить домен на новый IP. Клиенты ничего не заметят, подписки и ссылки продолжат работать.
- **Если по голому IP**, у ссылок-подписок поменяется адрес, и пользователям нужно будет добавить новую ссылку или QR. Поэтому для подписки и панели рекомендуем домен, хотя бы бесплатный. Мастер переезда об этом напомнит.

**Перенос с виртуалки на VPS** — первый настоящий сценарий: настраиваем и тестируем на VM, делаем копию, восстанавливаем её на VPS и меняем адрес для клиентов.

## 7. Логи и наблюдаемость

Три отдельных потока:

| Поток | Что внутри | Хранение |
|---|---|---|
| Системные логи | stdout/stderr ядер, ошибки агента и панели, перезапуски | кольцевой буфер на ноде + SQLite в панели, 7 дней |
| События | подключение и отключение, превышение лимита, истечение срока, нода упала или поднялась | SQLite, 90 дней |
| Аудит | кто из админов что изменил (с diff) | SQLite, без ограничения |

- Все логи структурированные (JSON): `ts, level, node, source, user, msg, fields`.
- В UI: живой хвост через WebSocket, фильтры (нода, источник, уровень, пользователь), текстовый поиск, пауза и автопрокрутка, экспорт.
- Access-лог Xray (куда ходил пользователь) по умолчанию выключен. Включается вручную на конкретной ноде с предупреждением.
- Метрики: трафик по пользователям, нодам и инбаундам в разбивке по часам; CPU, RAM, сеть и аптайм нод; графики на дашборде.

## 8. Безопасность и скрытность панели

Цель: сканер или случайный человек, нашедший IP сервера, не должен понять, что на нём есть панель. Человек с доступом к трафику не должен ничего перехватить. Ни одна форма или API не должны давать внедрить код, SQL или команду.

### 8.1 Скрытие панели (слои, включаются независимо)

| Слой | Как работает | По умолчанию |
|---|---|---|
| Случайный порт | установщик выбирает свободный порт из 20000–60000 (можно задать свой) | вкл |
| Секретный путь | всё, включая UI, API и статику, живёт под `/<секрет>/`, например `https://IP:42000/iui9V56dmVAz3b3g5V/`. Секрет — 18+ случайных символов (≥100 бит), генерируется при установке | вкл |
| Маскировка | на любой запрос не по секретному пути панель отвечает так же, как пустой веб-сервер. Режимы: `drop` (разорвать соединение без ответа), `404` (безликая 404), `proxy` (показать посторонний сайт-заглушку). Нет заголовка `Server`, нет favicon, title или JS до секретного пути, одинаковое время ответа | `404` |
| Только HTTPS | обычного HTTP нет вообще (кроме `127.0.0.1` в режиме разработки). Источники сертификата, по приоритету: **(1)** короткоживущий сертификат Let's Encrypt на IP-адрес (профиль `shortlived`, ~6 дней, автообновление каждые ~3 дня, как в свежих 3x-ui), домен не нужен, браузер не ругается; **(2)** ACME на свой домен; **(3)** самоподписанный ECDSA как запасной вариант. Подписка использует тот же сертификат. Продление ведёт сама панель (Go-библиотека ACME), без cron и acme.sh | вкл |
| Клиентский сертификат (mTLS) | панель принимает TLS-соединение только от браузера с нашим сертификатом (файл `.p12` импортируется в браузер или телефон). Без сертификата рукопожатие TLS обрывается, и сканер не видит даже 404. Это самая сильная защита, о ней ты и читал | выкл, включается одной кнопкой с предупреждением «сохрани .p12, иначе потеряешь доступ» |
| Белый список IP | доступ только с указанных IP или подсетей | выкл |
| Только через свой VPN | панель слушает внутренний адрес и доступна только из нашего VPN-туннеля или через SSH-туннель (`ssh -L`) | выкл, опция для параноиков |
| Отдельный адрес подписки | `/sub/...` работает на другом порту и пути, чем панель. Утечка ссылки подписки не раскрывает панель | вкл |

**Про сертификаты Let's Encrypt на IP (важные нюансы):**
- Плюс: настоящий доверенный сертификат вместо самоподписанного. Самоподписанный сертификат на нестандартном порту сам по себе заметен сканерам, а с настоящим панель похожа на обычный сайт. Короткий срок жизни: даже если ключ утечёт, через несколько дней он бесполезен, а отзыв сертификатов браузеры проверяют плохо, поэтому короткий срок надёжнее.
- Минус: каждый выпущенный сертификат попадает в публичные журналы Certificate Transparency (crt.sh). По ним видно, что у IP есть HTTPS, но не видно порт и путь. Секретный путь и mTLS остаются главной защитой.
- Для проверки владения IP Let's Encrypt стучится на порт **80** (http-01) или **443** (tls-alpn-01). Порт 443 будет занят Reality, поэтому панель на пару секунд при выпуске поднимает ответчик на 80-м и сразу его закрывает. Поддержку профиля `shortlived` в Go-библиотеке ACME (lego или `x/crypto/acme`) проверяем в фазе 0.
- Если 80-й порт закрыт хостером или ACME не сработал, используется самоподписанный сертификат с отпечатком для проверки, и в UI появляется предупреждение.

Если доступ потерян (забыл путь, потерял `.p12`), его можно восстановить только с консоли сервера: `panel admin show-url`, `panel admin reset-mtls`, `panel admin reset-password`.

### 8.2 Защита от перехвата
- Везде TLS 1.2+ (лучше 1.3) с современными шифрами. HSTS. Сертификат панели можно закрепить (показывается его отпечаток для проверки при первом входе).
- Cookie сессии: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/<секрет>/`. Сессии хранятся в БД как хэш, их можно отозвать. Сессия живёт ограниченно, при простое истекает.
- `Referrer-Policy: no-referrer`, чтобы секретный путь не утёк через Referer на внешние ссылки.
- Повторный ввод пароля или 2FA для опасных действий: смена пароля, отключение mTLS, экспорт бэкапа.
- Связь панели и агента: mTLS с собственным CA панели, отпечатки закреплены, агент не принимает команды ни от кого другого.

### 8.3 Защита от подбора и взлома входа
- argon2id для паролей, TOTP 2FA (рекомендуется сразу после установки).
- Лимит попыток входа по IP с растущей задержкой и временным баном. Ошибка входа всегда одинаковая («неверный логин или пароль»), и время ответа одинаковое, даже если логина не существует.
- Уведомление в Telegram о каждом входе и о серии неудачных попыток. Список активных сессий, «выйти везде».

### 8.4 Защита от инъекций
- **SQL:** только параметризованные запросы (`?`), никакой склейки строк. Позже сгенерированные sqlc-запросы.
- **Команды ОС:** агент вызывает внешние программы только через `exec.Command(prog, args...)` без shell. Значения из UI никогда не попадают в строку команды. Пути и имена проверяются по белым спискам.
- **Конфиги ядер:** собираются из Go-структур и сериализуются (`json.Marshal`, YAML-энкодер), никаких текстовых шаблонов со вставкой пользовательских строк.
- **Ввод в API:** строгий JSON: `Content-Type: application/json`, лимит размера тела, отказ при неизвестных полях, валидация каждого поля (длина, символы, диапазоны).
- **XSS:** React экранирует вывод, `dangerouslySetInnerHTML` запрещён линтером. Строгий CSP: `default-src 'self'`, без inline-скриптов и `eval`, `frame-ancestors 'none'`, `base-uri 'none'`.
- **CSRF:** cookie `SameSite=Strict`, запись только с JSON (браузер не может отправить такой запрос с чужого сайта без CORS), проверка заголовка `Origin`. CORS выключен.
- **Path traversal:** статика отдаётся только из встроенной в бинарь ФС, пользовательские пути не открываются.
- **SSRF:** функции, которые ходят наружу («проверить выход», скачать гео-базы по URL), не обращаются к локальным и приватным адресам и метаданным облака.
- **Clickjacking:** `X-Frame-Options: DENY`, `frame-ancestors 'none'`.

### 8.5 Прочее
- Секреты (ключи Reality, WARP, ключи Amnezia) хранятся в БД зашифрованными мастер-ключом из файла `0600` на диске.
- Сервисы работают от отдельного пользователя `panel` с минимальными правами. Права root нужны только агенту и только для firewall и sysctl, через capabilities systemd (`CAP_NET_ADMIN`, `CAP_NET_BIND_SERVICE`), а не полный root.
- Бинари ядер (Xray, Hysteria) скачиваются только с официальных релизов GitHub с проверкой контрольных сумм.
- Зависимости зафиксированы (`go.sum`, `package-lock.json`). В CI `govulncheck` и `npm audit`.
- Бэкап: экспорт БД и конфигов архивом, по расписанию в локальную папку или в Telegram, архив зашифрован паролем.

### Готовность к переезду на VPS

Решение (2026-11-04): на VPS переезжаем, когда **все функции работают на виртуалке**, а после переезда остаётся только финишная полировка. Порядок работ:

1. [ ] **Журнал:** живые логи ядер и панели с фильтрами, события (лимиты, сроки, падения ядер, входы в панель), аудит действий.
2. [ ] **Настройки и безопасность:** адрес для клиентов, смена пароля, 2FA (TOTP), активные сессии и «выйти везде», порт, секретные пути и маскировка из UI.
3. [ ] **Пользователи и статистика:** периодический сброс трафика, продление в один клик, онлайн и IP, трафик по дням, графики на обзоре.
4. [ ] **Страница подписки для людей** (`/sub/<token>` в браузере): QR всех способов, остаток трафика и срок, кнопки «добавить в приложение».
5. [ ] **Маршрутизация:** пресеты-переключатели, WARP, DNS, гео-базы с автообновлением (раздел 6).
6. [ ] **Система сервера:** BBR и sysctl, свой firewall на nftables (порты подключений), port hopping для Hysteria2.
7. [ ] **Сертификаты и домены:** DuckDNS и свой домен через Cloudflare (DNS-01 работает и на VM), протоколы через TLS/CDN, NaiveProxy; сертификат Let's Encrypt на голый IP — единственное, что проверяется только на VPS.
8. [ ] **Amnezia:** вкладка только для чтения, ключи `vpn://` в карточке пользователя.
9. [ ] **Обслуживание:** резервная копия и восстановление, обновление ядер и панели (фаза 2.5), Telegram-уведомления и автобэкапы.
10. [ ] **Установщик одной командой** для чистого VPS.
11. [ ] Переезд: копия с VM → VPS, замена 3x-ui, перевод портов на 443.
